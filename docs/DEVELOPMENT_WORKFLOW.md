# Процесс разработки «Слабого тела»

Срез инструментария и репозитория: 26.10.2026. Информация о подключениях относится к текущей сессии и может измениться.

## Текущая архитектура

- Сервер — Node.js ES modules, встроенный `node:http`, `server.mjs`; минимальная поддерживаемая версия согласно README — Node.js 20+.
- Клиент — одностраничное приложение на HTML/CSS/JavaScript: `index.html`, `program-library.js`, `coach.js`; административный интерфейс — `admin.html`. Отдельного сборщика и `package.json` сейчас нет.
- Данные аккаунтов и приложения хранятся в `data/accounts.json`; аватары — в `data/avatars`. `data/nutrition-catalog.json` — каталог продуктов приложения, а не база пользовательских аккаунтов. Не открывать и не переносить пользовательские данные в рамках обычной разработки.
- Пользовательские данные синхронизируются с сервером; браузерный `localStorage` также используется приложением для локальных данных/совместимости.
- Авторизация — аккаунт с логином и паролем; сервер использует scrypt для хеширования пароля и HttpOnly-cookie для сессии. Внешний OAuth-провайдер в исходниках не обнаружен.
- Telegram Mini App подключается через официальный Telegram Web App JS. Это само по себе не подтверждает серверную проверку Telegram `initData` как способа входа.
- Поиск и штрихкоды продуктов запрашиваются сервером у Open Food Facts (`search.openfoodfacts.org` и `world.openfoodfacts.org`). Приложение содержит резервный локальный каталог.
- Telegram-уведомления реализованы в коде через Bot API и webhook, но их доступность зависит от сетевого выхода VPS к `api.telegram.org`. Работоспособность production-соединения не подтверждается локальной проверкой.
- В обследованных клиентских и серверных исходниках аналитический SDK не найден. Публичный сервер, журналы хостинга и фактические настройки мониторинга в ходе локального аудита не проверялись.

## Рабочий цикл

1. Прочитать `AGENTS.md`, `README.txt`, `PROJECT_SPEC.md`, релевантные спецификации/бэклог и исходники.
2. Снять `git status --short`, `git diff --stat`, затем изучить дифф только тех файлов, которых касается задача. Сохранять все изменения рабочей копии; не делать reset/clean и не перезаписывать существующие неотслеживаемые файлы.
3. Для крупного изменения согласовать продуктовые развилки и план. Для локальной задачи предпочитать маленькие изолированные правки, совместимые с текущим сервером и JSON-схемой.
4. Проверить синтаксис/доступные проверки и пользовательский сценарий на изолированных синтетических данных. Не использовать `data/accounts.json` для тестов.
5. В отчёте разделять выводы по исходникам, реальные проверки, предположения и то, что не проверялось.

## GitHub, ревью и задачи

Когда GitHub-коннектор видит репозиторий:

- Использовать `BACKLOG.md` как продуктовый перечень до синхронизации GitHub Issues; не создавать дубли задач.
- Значимые изменения вести в короткоживущей ветке от актуальной основной ветки и оформлять PR с описанием сценария, тестов, миграций и отката.
- Перед слиянием проверять diff, защищённые API, результаты CI и открытые замечания ревью. Не выполнять merge или push без прямой просьбы.

Локальная копия имеет `origin` на этот адрес и ветку `main`, однако доступ через коннектор к Issues, PR и CI не подтверждён. Владелец должен разрешить GitHub-приложению доступ к этому репозиторию/организации, если хочет пользоваться этими операциями.

## Локальный запуск, тесты и выпуск

- Запуск — `node server.mjs`, по умолчанию `http://localhost:8766/`. Статический предпросмотр HTML не заменяет серверные API и авторизацию.
- Для тестов выбирать отдельные `RITM_DATA_DIR` и порт. Нельзя запускать сценарии регистрации, удаления или очистки на общей пользовательской папке данных.
- До выпуска сравнить исходники с активным серверным релизом и включать в архив только нужные файлы. Не включать `data/accounts.json`, `data/avatars`, `.env`, SSH-материалы, токены, пароли или резервные копии.
- Публикация требует HTTPS reverse proxy, постоянной папки данных и `RITM_SECURE_COOKIE=1` согласно README. Изменения сервера, БД/данных, DNS, секретов и production-конфигурации выполнять только по отдельному прямому разрешению.
- Перед обновлением использовать защищённый бэкап и план отката из `README.txt`/`deploy/`; старый релиз и пользовательские данные не удалять.
