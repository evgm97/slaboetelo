# Стратегия тестирования

Срез средств проверки: 26.10.2026.

## Что имеется сейчас

- Локальный сервер Node.js ES modules, запуск по `README.txt` командой `node server.mjs`.
- Node.js 24.19.0 доступен в текущей среде; проект заявляет поддержку Node.js 20+.
- `package.json`, npm-скрипты, CI-workflows и отдельные `*.test.*`/`*.spec.*` файлы в репозитории не обнаружены.
- `deploy/test-telegram-mock.mjs` — точечный перехват `fetch` для методов Telegram `getWebhookInfo` и `sendMessage`, а не тестовый раннер. Остальные методы (например `setWebhook`) не перехватываются и могут попытаться обратиться к сети. Не использовать этот mock как гарантию изоляции скрипта настройки webhook.
- Ручная проверка интерфейса доступна через встроенный браузер/CUA. Подключённого автоматизированного браузерного набора в репозитории нет.

## Проверки перед изменением

1. Зафиксировать `git status --short` и `git diff --stat`; сохранить все существующие изменения.
2. Найти соответствующие API, структуру данных и клиентский сценарий. Не считать наличие экрана доказательством сохранения данных.
3. Определить риск: чисто визуальный, обратимая логика, схема хранения, права доступа, внешняя интеграция или production.

## Базовые локальные проверки

Для изменения серверного/клиентского JavaScript выполнить подходящие синтаксические проверки без установки пакетов:

```powershell
node --check server.mjs
node --check coach.js
node --check program-library.js
node --check nutrition-source.mjs
```

Запуск приложения проводить только с отдельной папкой тестовых данных и свободным портом, например:

```powershell
$testDataDir = Join-Path $env:TEMP ("slaboetelo-test-" + [guid]::NewGuid().ToString("N"))
$env:RITM_DATA_DIR = $testDataDir
$env:PORT = "8767"
node server.mjs
```

Не задавать `RITM_DATA_DIR` на путь к рабочей `data`; не копировать туда настоящие аккаунты. Оставлять временные данные до завершения проверки, если они нужны для воспроизводимости. Не запускать тесты, которые меняют или удаляют реальные данные.

## Минимальная матрица сценариев

| Область | Проверить |
|---|---|
| Авторизация и аккаунты | Регистрация/вход тестового аккаунта, cookie-сессия, выход, повторный вход; отказ API без сессии. |
| Синхронизация | Сохранение в тестовом аккаунте, перезагрузка и повторное чтение; пользовательские данные изоляционно отделены. |
| Тренировки и программы | Частичное/полное выполнение, остановка и восстановление сессии, согласованность программы/календаря/статистики, неизменность истории при сбросе прогресса. |
| Замеры | Добавление, изменение, дата, история версий, график, сохранение после перезагрузки. |
| Тренер/клиент | Отдельные синтетические аккаунты, согласие/отзыв связи, проверки всех серверных разрешений, запрет утечки непредоставленных данных. |
| Питание | Поиск/штрихкод, сохранение продуктового снимка, неизвестные нутриенты не превращаются в ноль, понятный отказ внешнего каталога. |
| Telegram | Тестовый mock и синтетические чаты; отдельно фиксировать, что mock покрывает только перечисленные методы. Живой Bot API проверять только при явно настроенной тестовой интеграции и согласованном тестовом аккаунте. |
| Адаптивность | Узкий мобильный viewport, длинные названия, клавиатура, фиксированная навигация, модальные окна, горизонтальное переполнение; отдельно WebView Telegram, если доступен. |
| Админ API | Отказ неавторизованной сессии и разрешение только администратору на каждом endpoint. Не тестировать на владельческой production-сессии без прямой необходимости. |

После теста записать команду, устройство/viewport, синтетические данные, ожидаемое и фактическое поведение. Скриншот и ручной осмотр не заменяют серверную проверку разрешений.

## Ограничения и будущий рост

- Пока нет CI и тестового раннера, поэтому автопроверки означают только реально выполненные `node --check`/скрипты; не писать «тесты пройдены», если запускался только браузер.
- Перед установкой Playwright/Vitest/ESLint сначала определить конкретную пользу, влияние на размер/обслуживание проекта и стоимость поддержки. Добавлять зависимости отдельным согласованным изменением.
- Будущий CI должен работать без `data/accounts.json`, токенов, реальных chat ID и доступа к production. Внешние сервисы в CI заменять mock-ответами.
