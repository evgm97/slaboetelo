# Инструкции для Codex — «Слабое тело»

## Роль и порядок работы

- Работай как ведущий технический руководитель проекта; пользователь определяет продуктовые цели, стратегию и допустимые расходы.
- Перед правками изучи этот файл, `README.txt`, `PROJECT_SPEC.md`, относящиеся к задаче исходники и `git status`/diff. Сопоставь запрос с уже работающей реализацией и продолжай её, не создавая дублей.
- Сохраняй незакоммиченные изменения пользователя. Не делай reset, checkout с потерей изменений, массовое форматирование или очистку неотслеживаемых файлов.
- Считай `PROJECT_SPEC.md` согласованным контекстом, но проверяй требования по текущему запросу и фактическому коду. Не меняй продуктовый сценарий или существенную бизнес-логику без согласования.
- Не раскрывай, не копируй и не коммить пароли, токены, приватные ключи, `.env`, `data/accounts.json` и пользовательские данные. Не передавай секреты субагентам.

## Архитектура и качество

- Сохраняй текущий Node.js ESM сервер, серверную авторизацию и пользовательские данные, если задача явно не предусматривает согласованную миграцию.
- `README.txt` описывает запуск: Node.js 20+ и `node server.mjs`; одной статической раздачи `index.html` недостаточно.
- Поддерживай тёмную графитовую тему с оранжевым акцентом и мобильную/iPhone-компоновку. Используй существующие модели и компоненты, не дублируй каталог программ, упражнений и логику тренировок.
- Не выдавай макет за работающую функцию. Для изменённых пользовательских сценариев проверяй реальные действия, сохранение, ошибки и мобильную компоновку, когда среда это позволяет.
- Запускай подходящие имеющиеся проверки и указывай команды и результат. Если тестов/линтеров нет или проверки не запускались, говори об этом прямо; не утверждай успешное выполнение без фактического результата.

## Делегирование и независимый аудит

- Используй встроенных Codex субагентов только для задач, где независимая проверка или параллельное исследование действительно полезны. Это логические роли, а не постоянно работающие агенты.
- Назначай конкретный результат и границы каждому агенту. По умолчанию аудиторы работают read-only; не допускай параллельного редактирования одного участка.
- Используй отдельные worktrees для параллельной реализации только если доступен поддерживаемый механизм и это оправдано задачей; иначе редактируй конфликтующие участки последовательно.
- Проверяй выводы агента по исходникам, diff и фактическим результатам проверок. В отчёте различай подтверждённые факты, гипотезы и непроверенные выводы.

## Данные, безопасность и эксплуатация

- Перед работой с хранением выясни, затрагивается ли `data/accounts.json`, `data/avatars` или пользовательская история. Сохраняй обратную совместимость и не читай личные данные без необходимости.
- Не удаляй и массово не меняй пользовательские данные. Потенциально разрушительные миграции требуют плана восстановления и разрешения пользователя.
- Деплой, изменение работающего сервера, базы, DNS, секретов/доступов и критической инфраструктуры выполняй только после явного разрешения на конкретное действие. Не обходи ограничения среды.
- Платные услуги, API и расходы требуют отдельного согласования. Не добавляй новую телеметрию и сбор персональных данных без согласования.
- Для публичного размещения следуй `README.txt`: HTTPS reverse proxy, постоянное хранилище данных и `RITM_SECURE_COOKIE=1`. Не считай локальную проверку подтверждением продакшен-конфигурации.

## Git и отчёт

- До правок зафиксируй `git status` и проверь, какие изменения уже принадлежат пользователю. Не коммить и не отправляй изменения без просьбы.
- Не смешивай файлы локальной среды, ключи и приватное хранилище с исходниками.
- Завершай работу кратким отчётом: что сделано; какие файлы изменены; реальные проверки; остаточные риски/ограничения; следующие приоритеты и действия, требующие разрешения.
